## 不直接启用原版 runtime 的原因

原版已经解决部分桌面宿主兼容和工具白名单问题，但与大肥鱼现有管理边界仍有差异，不能只关掉一个“自动评论”开关就整体挂载：

1. `index.js` 的默认 `dmWatch:true`、`dmMode:'only'` 会把私信相关路径一起带入；源码注释和 README 对默认状态还存在不一致。
2. `bili_reply` 的 `force:true` 由模型参数控制，可以越过自动评论关闭门禁；`bili_config` 允许模型改包括自动评论在内的配置，执行体没有核验大肥鱼当前账号身份。
3. HTTP 只检查 `connection.requestRejection` 与同源，未要求 `connection.admit(req).peer.principal.kind === 'owner'`。离线 fixture 中，模拟“连接已准入但 principal 为 guest”后，读取配置及将 autoComment 改为 true 均返回 200。这证明缺少本项目要求的 owner 门禁，不等于已证明真实服务对公网开放。
4. `GET /status` 会归档和拆分报告写盘；配置写入不采用本项目的版本 CAS 与私有原子事务。不能把这些路由当作大肥鱼被动状态接口。
5. `apply()` 会铺设独立 `profiles/bili-duty` 和后台监听；本项目已统一管理自主活动、控制授权、消息优先级及任务恢复，直接启用会产生第二套执行体系。

对应原始代码：[宿主注册、配置、工具、路由](https://github.com/c1overzz/dsh-bili-scroll/blob/5be5f6d57c47c7e79ad9bc4ce39457b68a160dfa/index.js)、[MCP 白名单与写操作 guard](https://github.com/c1overzz/dsh-bili-scroll/blob/5be5f6d57c47c7e79ad9bc4ce39457b68a160dfa/vendor/bilibili-mcp/mcp_server.py)。

## 浏览适配清单

已生成 `staging/bili-readonly-launch.json`，保持 `enabled:false`。独立 MCP 的 `BILI_MCP_TOOLS` 必须固定为以下非空名单：

```text
bili_search,bili_subtitle,bili_comments,bili_video_info,bili_cover,bili_frames,bili_danmaku
```

前期纯装饰器/guard AST fixture 验证了只注册这 7 项并拒绝两个写操作；后续已经启动真实 MCP，`initialize → initialized → tools/list` 返回的名单也精确等于这 7 项。模块每次启动都重新核对，多一项、少一项、重复或名单为空均停止；不依赖一次安装记录。该环境变量为空时，上游行为是全部注册，不能省略。

后续适配必须满足：

- 可执行文件、脚本、私有状态、凭据路径由本机受管配置固定，模型不能传路径、URL、命令或环境变量。凭据只属于新独立账号；目录 0700、文件 0600。
- 不调用上游 `index.js`，不启用其后台定时器、HTTP 管理、配置工具、自动评论或私信。报告写入由大肥鱼现有受控存储处理。
- 从真实执行上下文检查主人和会话；异步完成后重查取消、运行实例与账号身份。附加账号继续保持原有两项本人经历工具边界。
- 自主浏览复用既有 Life/controlAccess 的用户优先、域名和时间规则，网页文字只作资料，不作为新的授权。
- 搜索词、结果数量、BV 号、抽帧数量和输出大小须有界；超时、取消、风控和缺字幕分别如实返回。不能把抽取几帧描述成完整看完视频。
- 不以注册成功或账号已登录标记“浏览已验证”。验收需真实完成检索 → 读取字幕或帧 → 回读视频 BV 号和来源，含取消和失败路径。

## 受管浏览模块与实测

仓库新增 `packages/dsh-dafeiyu/src/bili-browser.js`，18 项隔离测试通过。构造函数及 `status` 不创建目录、不启动进程、不请求网络。`check/call/probe` 只接受受控的 `authorize` 回调和取消信号；启动时核对固定源文件 SHA-256，复制到私有状态目录，使用固定 Python `-I -B` 和精确环境白名单启动，每次操作后等待真实子进程退出。超时/取消会停止进程；清理不能确认时保留占用并拒绝新操作，不自动重试。

供宿主集成的接口：

```js
const browser = new BiliBrowser({
  pythonPath, scriptPath, stateDir, scriptSha256, enabled,
});
browser.status; // 纯内存：enabled/configured/active/cleanupPending/最近证据
await browser.check({ authorize, signal }); // 显式核对真实7项工具
await browser.call('bili_search', { keyword: 'DeepSeek Harness', num: 3 }, { authorize, signal });
await browser.probe({ authorize, signal }); // 公开检索→字幕或抽样画面→BV一致性
await browser.dispose(); // 等待实际子进程退出，未知清理不假装成功
registerBiliBrowserTools(ctx, { browser, getExecutionContext, controlAccess });
```

注册工具名 `dafeiyu_bili_browse`，只允许 7 项 operation。逐次核验真实主人 session、同一 `controlAccess.scopeFor(agent)` owner task 与 browser 能力；异步完成及保存图片附件后再次核验。API 数据读取不占用或操作 Ego 共享界面。模型不能指定程序、路径、URL、Cookie、环境变量或操作其他账号。工具参数/输出通过当前桌面版 0.2.1-rc.2 的真实宿主 schema 校验；模型呈现使用该版本支持的子集，完整长度/数量界限仍在执行端严格校验。

## 投稿的最小方案

用已下载的 arm64 biliup CLI 处理本地视频，不启动其服务器、直播录制或 WebUI。不要裸跑可执行文件：本版空命令会默认启动 server。`upload` 会最终提交，没有 draft/dry-run，不能当作无外部影响的测试。[固定版 CLI 参数](https://github.com/biliup/biliup/blob/95e67857f943f0ea90263668c79191784e94421a/crates/biliup-cli/src/cli.rs)。

独立账号完成原生登录后，以 `spawn/execFile` 固定 argv 调用；只允许受管凭据文件和本次已确认的本地视频、封面、标题、简介、分区和标签。命令模板、参数与隔离验证日志见 `research/biliup-notes.md`、`research/biliup-evidence.json`。本轮没有执行登录或投稿模板。

原版 CLI 丢弃最终 `ResponseData`，没有结构化 receipt 输出；上传 checkpoint 在最终提交前删除。因此不能根据退出码、成功文案、断点续传文件或日志里随意出现的 BV 号确认成功。最小后续改造是固定源码，补一个窄的原子 receipt 输出，精确保存本次最终返回的 code / aid / bvid；不更换整套投稿实现。[提交与 checkpoint](https://github.com/biliup/biliup/blob/95e67857f943f0ea90263668c79191784e94421a/crates/biliup-cli/src/uploader.rs)。

防重复与结果验收合同：

1. 准备时固定账号 mid、视频/封面 SHA-256、规范化标题等元信息哈希和本次授权标识。一次授权对应稳定任务键，同账号互斥覆盖上传、提交、回查全过程。
2. 启动外部进程前落盘 `dispatching`。只允许 prepared → dispatching → submitted → verified；进程启动后的超时、取消、崩溃、重启或缺少精确回执一律保留 unknown，禁止重放、自动换投稿器或把 running 清回 pending。
3. 只接受本次受控 receipt 的 `code=0`、合法 aid 和 `BV` 加 10 位字母数字的 bvid，先持久记录 submitted，再读回。提交接受与审核通过、公开可见分别表达。
4. 使用同账号稿件详情核对 aid/bvid、所属账号、标题、简介、分 P 数等；审核中稿件可能暂时不能公开查询。回查失败保持待核实，绝不因此重新投稿。[提交/稿件接口](https://github.com/biliup/biliup/blob/95e67857f943f0ea90263668c79191784e94421a/crates/biliup/src/uploader/bilibili.rs)。
5. 没有 bvid 的未知任务须人工或受控列稿核对；“没查到”不能自动解除防重。成功、明确失败、未知和取消均通过现有 QQ 回传单独去重。
