# QQ 文件消息误报：修复与真实界面验收（2026-10-27）

## 具体原因

通过现有 OneBot 连接做只读身份核验，再查询绑定主人最近 3 条消息，仅提取时间、是否绑定发送方和消息段类型，不检查正文、文件名、路径或内容。与 18:54:08 失败对应的最近入站消息发生于 18:54:06，只有 `file` 段，且没有 raw.text 字段。

原入口的路径是：QQGateway 不处理 file 段，将其归一为空文本；首次准入为语音准备保留空文本；非语音的 prepare 原样返回；第二次文本验证拒绝空内容，最终把不支持的文件消息记成 `prepare_failed`。这解释了该次毫秒级失败，模型尚未调用。原流程没有保留底层堆栈；归因依据为匹配的时间、消息段类型和同结构的实际装配复现。没有证据把它归因于 STT、模型服务商或网络。

## 已修复范围

- 统一检查实际 file 消息段与旧 CQ 文件格式，不读取文件名、路径或字节。
- 文件及混合文件消息进入有去重证明的队列后，明确归为 `unsupported_input`；混合文件不能绕过准备阶段触发后台命令，也不把附件占位符送模型。
- 无可处理文字的消息归为 `empty_input`，不再一律冒充准备函数异常。
- 仅对未来新收到的此类消息给一次固定提示；沿用接收方、连接代际、取消、回执和去重保护，送达未知继续 blocked / requiresAck，不重发。
- 首页以中性“消息需要补充”说明已知输入问题，显示对象、时间及固定原因；聊天未暂停时不提供多余的恢复按钮。内部异常、暂停或未知结果仍优先告警，保留原恢复 CAS 和确认保护。
- 旧 `prepare_failed` 不自动改写原因、不恢复、不补发或重跑。

**本轮没有接入 QQ 文件读取能力。** 文件仍不会自动下载或交给模型；现在会明确说明这一限制，不会假装已读附件或把它误报为系统故障。
